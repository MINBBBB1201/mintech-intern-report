# 4M 품질분석 코드 설명

해당 제조사 인턴십 이후 작업 조건을 데이터로 표현하는 분석 예제를 만들었다. 4M 변수와 작업시간, 재작업 항목을 입력으로 두 분류모델의 결함 탐지와 오경보를 비교했다. 데이터 4,000행은 코드로 생성했으며 회사 생산 기록은 사용하지 않았다.

## 데이터와 목표값

| 컬럼 | 내용 |
|---|---|
| `worker_id`, `shift` | 작업자 코드와 교대 |
| `machine_id` | 설비 코드 |
| `material_lot` | 자재 로트 |
| `task_id` | 작업 코드 |
| `active_s`, `wait_s` | 활동시간과 대기시간 |
| `retry_count`, `rework` | 재시도 횟수와 재작업 여부 |
| `defect` | 생성 규칙으로 부여한 결함 라벨 |

`elapsed_s`와 `total_time`은 모두 활동시간과 대기시간의 합이다. 중복된 두 값 중 모델에는 `total_time`만 넣는다. 대기비율과 재시도 파생값도 행 단위로 계산한다. 코드의 `retry_per_min`은 `retry_count / (active_s / 60 + 1)`로 계산한 정규화 지표다. 분모에 1을 더하므로 실제 분당 재시도 횟수와 구분한다.

`defect`는 독립적으로 관측한 현장 결함이 아니라 생성 라벨이다. 각 행에서 `material_lot % 7 == 0`, `shift`, `rework`, 평균을 뺀 `wait_s`와 정규잡음으로 점수를 계산하고, 점수가 높은 `int(n * defect_rate)`개 행을 양성으로 지정한다. 기본 실행에서는 4,000행 중 240행이다. `rework`와 시간 변수는 작업 중이나 완료 후에 확보되며 라벨 생성에도 쓰이므로, 이 결과는 독립적인 현장 결함 예측 성능이 아니라 합성 규칙을 복원하는 작업 완료 후 분류 예제다.

## 실행

```bash
pip install -r code/requirements.txt
python code/pipeline.py --n 4000 --defect-rate 0.06 --seed 42 --out outputs
streamlit run code/app/dashboard.py
```

기본 seed는 42다. LightGBM이 없으면 RandomForestClassifier로 대체하며 실제 모델 이름을 출력에 남긴다. 의존성은 최소 버전 범위로 지정되어 있으므로 환경에 따라 결과가 달라질 수 있다.

## 처리 흐름과 설계 선택

1. 4,000행을 생성하고 240행을 양성으로 지정한다.
2. 데이터 전체의 집계값을 피처로 쓰지 않고 행 단위 파생값을 만든다.
3. 75/25 층화 분할로 테스트셋 1,000행을 분리한다.
4. 범주형 변수를 원핫 인코딩하고 두 모델을 학습한다.
5. 임계값 0.5에서 혼동행렬과 성능 지표를 계산한다.
6. 데이터, 평가값, 실행 조건을 `outputs/`에 저장한다.

분할은 행 단위 무작위 층화 분할이다. 같은 작업자·설비·작업·로트 코드가 학습셋과 테스트셋에 함께 나타날 수 있으므로 미래 기간, 신규 로트, 신규 작업자나 신규 설비에 대한 일반화 성능을 검증하지 않는다. 기본 실행의 학습셋은 3,000행과 양성 180건, 테스트셋은 1,000행과 양성 60건이다.

ROC-AUC와 F1 외에 `average_precision_score`로 AP를 계산한다. 기존 출력의 열 이름 `pr_auc`는 유지했으며 적분 방식의 PR 곡선 면적과 혼동하지 않도록 AP로 설명한다. Isolation Forest는 참고용으로 실행하고 콘솔에 precision을 출력하지만 결과 CSV에는 저장하지 않는다.

## 저장된 결과

| 모델 | ROC-AUC | AP (`pr_auc`) | F1 | TN | FP | FN | TP |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| LogisticRegression | 0.9166 | 0.4604 | 0.4367 | 821 | 119 | 10 | 50 |
| LightGBM | 0.9035 | 0.4849 | 0.4522 | 911 | 29 | 34 | 26 |

테스트 결함 60건에서 LogisticRegression의 재현율은 83.3%(50/60), 정밀도는 29.6%(50/169)다. LightGBM은 각각 43.3%(26/60), 47.3%(26/55)다. 놓친 결함과 오경보 중 어느 비용을 줄일지에 따라 모델 선택이 달라진다. 한 번의 분할과 단일 임계값으로 얻은 결과라서 현장용 모델의 우열은 확정하지 않았다.

`pr_auc` 열은 `average_precision_score`로 계산한 AP다. `FN`은 생성 라벨이 1이지만 임계값 0.5 미만으로 분류한 행이고, `FP`는 생성 라벨이 0이지만 임계값 이상으로 분류한 행이다. 이는 체크리스트 오류나 회사 생산 결함의 누락·오경보가 아니다. `class_weight="balanced"`를 사용하므로 임계값 0.5를 실제 결함 확률 50%나 운영 최적 임계값으로 해석하지 않는다.

## 대시보드

작업자, 설비, 작업, 교대로 분석 데이터를 필터링하고 그룹별 결함률과 시간을 집계한다. 화면의 상위 그룹은 결함 라벨의 관측 비율을 정렬한 결과다. 대시보드는 같은 seed로 데이터를 새로 생성해 집계하며 모델 예측은 실행하지 않는다. KPI 카드는 전체 생성 데이터로 계산하고, 차트와 표의 기본 필터는 작업자 0–3과 작업 0–7만 선택하므로 기본 실행에서는 1,341행을 표시한다. 두 값의 모집단이 다르다는 설명을 화면에도 표시한다.

## 파일 구성

```text
code/
  pipeline.py
  requirements.txt
  app/dashboard.py
outputs/
  4m_quality_analysis_data.csv
  results.csv
  run_metadata.json
```

비교분석 워크북은 완성 파일로 제공한다. 공개 제출 패키지의 재현 대상은 `pipeline.py`와 `app/dashboard.py`다.

캐리어와 쿠폰 기록을 검사하는 `record_validation.py`와 시험을 재현하는 `verify_records.py`도 함께 제공한다. 이 검증 도구는 체크리스트의 기록 구조를 다루며 4M 모델의 입력이나 예측 결과를 검사하는 도구는 아니다. 실행 방법과 결과는 [기록 검증 결과](software_validation.md)에 정리했다.
